## 一、空间账先算清楚

底部要塞进 80～110px 的事件模块，而 1080 高度原本已经排满。所以先算：

| 项 | 变化 |

| 事件模块 | 104px + 12px 间距 = 116px |
| 缺口 | 116 − 44 = **72px** |
| 处理 | 内容区 960 → **876px**，按比例分担到三栏 |

三栏新高度（合计均为 876）：

| 左栏 | 中栏 | 右栏 |
|---|---|---|
| 192 / 330 / 322 | 300 / 560 | 238 / 236 / 370 |

> 说明：不可能既加 104px 又不压缩任何模块。这里让每个模块各让出一点（左 −4/−28/−52，中 −36/−48，右 −12/−16/−68），保持相对比例与观感，没有单独牺牲某一块。

| 状态 | 颜色 | 判定 |

## 四、底部：实时运行事件

高度 **104px**，横向铺满内容区宽度，分三层：标题行（22px）／事件条（滚动）／状态行（12px）。

### 事件从哪来（关键：不造假）

新增 `RunEventMonitor`，每 150ms 对比**相邻两帧**的 DB120 与连接状态，只在**真实跃变**时记录：

| 触发条件 | 事件文案 | 级别 |
|---|---|---|
| 故障码 0 → 非 0 | 发生故障，故障码 N | 故障（红） |
| 故障码 非 0 → 0 | 故障已恢复 | 正常（绿） |
| 忙碌 0 → 1 | 开始供料 / 开始灌注 / 开始入库（订单 N） | 提示（蓝） |
| 完成位 FALSE → TRUE | 完成供料工序 / 完成灌注工序 / 完成入库工序 | 正常（绿） |
| 已接收 FALSE → TRUE | 已接收订单 N | 提示 |
| 订单号变化 | 载入订单 N / 订单切换 N → M | 提示 |
| 运行模式变化 | 进入自动运行 / 进入自动待机 / 切换为手动模式 | 正常 / 提示 |
| 在线 1 → 0 / 0 → 1 | 单元离线 / 单元恢复在线 | 警告（橙）/ 正常 |
| 通信 → Faulted | PLC 通信中断：<原因> | 故障（红） |
| 通信 → Connected | PLC 通信已建立 / 通信恢复 | 正常（绿） |
| CPU Run → Stop | PLC 进入 STOP，数据已冻结 | 警告 |

首帧只建立基线、不产生事件，避免一启动就刷一堆假记录。

### 交互与容量

| 要求 | 实现 |
|---|---|
| 最新优先 | 新事件插到最左 |
| 自动滚动 | 列表随新事件自动前移；可用横向滚动条翻看更早事件 |
| 暂停 | 暂停只冻结界面刷新，**采集与记录继续**（恢复后立即补齐） |
| 查看最近 | 显示「最近 N 条 · 累计 M 条」，界面最多 12 条，内存环形缓冲上限 300 条 |
| 不无限占内存 | 固定容量 300，超出丢最旧 |
| 持久化 | 追加写入 `%LOCALAPPDATA%\DLDS532\run-events.jsonl`（超过 4MB 自动转 `.old`）；启动时回读最近 12 条，避免开机空白 |

> SQLite 到阶段五再接：现在写 JSONL 是为了零依赖、可人工查看；届时把 `RunEventLog.Add` 的落盘实现换成 SQLite 插入即可，接口不变。

底部状态行合并了原来的版本号与「只读监控」说明，不再单独占一行。

## 五、验证

1. `dotnet build DLDS532.sln -c Release` → 0 警告 0 错误
2. 冒烟测试 44 项全通过，新增 7 项：
   - 首帧不产生事件
   - 忙碌跃变 → 开始供料
   - 完成跃变 → 完成供料工序
   - 故障跃变 → 故障级事件（含故障码）
   - 通信中断 → 故障级
   - 通信恢复 → 正常级

4. 逐页出图核对：`artifacts/r3_page0/1/2/5.png`
5. 标题居中实测：文字块 785~1135px，中心 960，与窗口中心一致
